# 지식베이스 정확도와 개발 시간 평가

[질문 기준](questions.json)은 원본 직접 탐색과 위키 활용을 비교하기 위한 초기 사례다.
문서 작성자가 이번 문맥에서 기대 근거를 작성했으며, 독립 응답 평가나 앱 실행 결과는 아직 없다.
사용자 목표는 정확한 지식 활용과 다섯 개발 방식의 검증 완료 시간 단축이다.
질문 평가는 초기 진단으로 사용하고, 최종 효과는 같은 범위의 실제 구현에서 측정한다.

## 실행 절차

1. `python3 scripts/knowledge.py check`로 자료와 문서 기준을 확인한다.
2. 같은 모델·추론 설정과 같은 질문을 사용한다. 새 문맥의 두 조건을 각각 준비한다.
   기준 조건은 원본 자료를 직접 탐색하고, 위키 조건은 목차·위키와 필요한 원본을 탐색한다.
   양쪽에 허용한 파일과 도구를 기록하며 응답 담당에게 `expected_points`를 주지 않는다.
3. 평가 담당이 두 응답을 원본·기대 근거와 대조한다. 출처가 정확한 주장에 붙었는지,
   필요한 조건을 빠뜨렸는지, 미확인을 확정했는지 각각 확인한다.
4. 질문별로 응답, 인용 출처, 충족/누락 항목, 오류와 판정 이유를 저장한다.
   실행 시간·사용량은 실제 도구가 보고한 값만 기록한다. 순서 효과를 줄이려면 조건 순서를 교차한다.
5. 원본 기준·질문 기준·위키 버전, 모델·도구, 날짜와 결과 위치를 [이력](../log.md)에 연결한다.

## 판정

각 질문의 `expected_points`와 근거를 확인한다. 요구 항목 충족·출처 적합·불확실성 구분을
각각 기록하며, AI 자동 점수만으로 의미 정확성을 확정하지 않는다.
모르는 플랫폼 정책을 추정하지 않는 것도 평가 대상이다. 근거 없는 실행·호환·완료 주장은 오류다.

질문 평가 통과는 실제 앱 동작 검증과 별개다. 초기 10개 사례의 통과만으로
다섯 플랫폼 전체의 지식 충족이나 개발 속도 개선을 결론내리지 않는다.

## 시간을 줄이기 위한 작업 구성

1. 공통 준비에서 기능 규칙·API 입력/응답·오류·화면 상태·검증 사례를 고정하고 모든 대상이 재사용한다.
2. 기존 코드·모델·검증 로직·자산의 재사용 가능성을 분류한다. 대상에서 실행 가능한지는 확인한 뒤 공유한다.
   계산 규칙과 테스트 입력/기대값은 언어와 분리해 공유할 수 있도록 표현한다.
3. 공통 기능 설명과 해당 플랫폼의 차이만 묶어 작업에 제공한다. 같은 원본 탐색과 불필요한 전체 문서 읽기를 줄인다.
4. 첫 기능의 계약과 각 대상 빌드·검증 방법을 확인한 뒤, 의존성이 없는 대상 작업을 제한된 슬롯에 배정한다.
   대상별 쓰기 폴더를 분리하고 공통 계약의 변경은 조정자가 관리한다. 공유 서버·DB 검사에는 기존 직렬화 규칙을 유지한다.
5. 빌드·응답 디코딩·주요 흐름을 일찍 확인해 차이를 발견하고, 실제로 반복되는 문제의 해결 근거를 위키에 반영한다.

이는 앞으로의 작업 설계다. 이번 문서 수정으로 에이전트나 앱 빌드를 실행하지 않는다.
기존 `agents/service.json`은 UI를 제외한 Rust 서비스 작업 설정이므로 다중 클라이언트 배정에 그대로 적용하지 않는다.
실제 대상 버전·OS·동시 실행 상한·역할을 정한 후 앱 작업을 배정한다.

## 측정할 시간

| 항목 | 측정 경계 |
| --- | --- |
| 초기 준비 | 원본 조사, 위키 구축, 공통 계약·검증 사례, 개발 환경 준비 |
| 첫 실행 가능 시점 | 각 대상에서 대표 흐름을 처음 실행할 수 있게 된 시각. 검증 완료와 구별 |
| 대상별 완료 시간 | 작업 배정부터 해당 대상의 같은 검증 기준을 모두 충족한 시각까지 |
| 전체 완료 시간 | 공통 준비 시작부터 모든 대상의 검사·리뷰·재작업과 필요한 위키 갱신이 끝난 시각까지 |
| 재작업과 유지 비용 | 오류 조사·수정·재검사, 위키 오류·오래된 설명 수정에 쓴 시간 |
| 대기와 사용량 | 모델·빌드 슬롯·환경·사용자 결정 대기, 실제 모델 사용량과 확인 가능한 비용 |

전체 완료 시간은 공통 시작과 마지막 대상 완료 시각의 차이로 기록한다.
병렬 대상의 시간을 단순 합산한 값은 전체 경과 시간이 아니다. 별도로 실제 작업 시간과 중복 구간을 남긴다.
실패·중단·검증 미완료는 성공한 빠른 실행으로 집계하지 않는다. 통화·날짜·취소·인증 등 검증 범위를
줄인 결과도 같은 범위의 속도 향상으로 비교하지 않는다.

## 비교 조건

- 기준 조건은 원본과 공식 자료를 직접 탐색하고, 위키 조건은 공통 위키와 원본·공식 자료를 활용한다.
  제품 코드·API 계약·공통 검증 사례는 양쪽에서 같은 기준을 사용한다.
- 같은 기능·원본/백엔드 기준·대상 OS·버전·모델·추론 수준·동시성 상한·리뷰 기준을 고정한다.
  기준 조건의 탐색에 위키와 평가 기대 답안을 노출하지 않는다.
- 기존 구현을 다음 조건에 전달하지 않고 격리된 작업 폴더와 새 문맥을 사용한다.
  실행 순서·의존성 캐시·도구 준비 상태와 인프라 차이를 기록하고 가능한 조건을 맞춘다.
- 전체 개발 시간 비교와, 이미 구축된 위키를 재사용할 때의 작업 시간 비교를 구분한다.
  현재 초기 구축 시간은 미계측이므로 0으로 계산하지 않는다. 총 투자 대비 효과를 평가하려면
  초기 준비를 새로 계측하거나 미계측 부분을 명시한 제한된 비교로 보고한다.
- 절감률은 비교 가능한 두 실행의 실제 시간이 모두 있을 때만 계산한다.
  `절감률 = (기준 조건 시간 - 위키 조건 시간) / 기준 조건 시간`으로 기록하고,
  단일 실행의 차이를 반복 실행에서도 재현되는 효과로 일반화하지 않는다.

품질은 기능 누락·출처 오류·실행 검사 실패·미해결 리뷰·사람의 수정 개입으로 함께 기록한다.
속도와 품질을 확인한 뒤 유지할 위키 내용과 작업 절차를 선택한다. 목표 절감률이나 완료 예상 시간은 아직 정하지 않았다.
