# 원문 보관과 위키 갱신 절차

이 지식베이스는 Karpathy의 LLM Wiki에서 제안한 원본·위키·운영 규칙 세 계층과
자료 추가(Ingest)·질의(Query)·점검(Lint) 흐름을 프로젝트에 맞춰 적용한다(E01).
원문은 고정 구현을 강제하는 표준이 아니라 구체적인 구성은 함께 정하는 패턴으로 설명한다.

| 원문의 역할 | 현재 위치 | 처리 방법 |
| --- | --- | --- |
| 원본 자료 | reference/, knowledge/raw/external/, sources.json | 코드는 원래 위치의 해시로 고정, 외부 응답은 출처별 해시 파일로 보관 |
| 위키 | knowledge/wiki/ | 근거·현행 동작·제안·미확인을 구분하며 관련 페이지를 연결 |
| 운영 규칙 | knowledge/AGENTS.md, knowledge/README.md | 자료 추가·질의·변경 확인·검증 방법을 규정 |
| 탐색과 이력 | wiki/index.md, log.md | 주제별 위치와 변경 이유·실패·남은 작업 기록 |

해시·후보 검토·플랫폼 문서 선택은 이 프로젝트에 추가한 장치다. 아래 명령은 원문 수집과
기준 지정을 담당한다. 자료의 의미를 읽어 위키에 통합하는 작업은 현재 대화의 에이전트가 수행한다.

## 자료 추가

1. sources.json에 출처 ID·공식 URL·확인 범위를 등록한다. 읽기 전 상태는 catalogued다.
   같은 문서의 공식 raw 표현이 있으면 snapshot_url에 별도로 기록한다.
2. 원문을 수집한다. 다음은 새 파일명을 사용해야 하는 실행 예다.

```sh
python3 scripts/knowledge_sources.py fetch --source E01 --output knowledge/evidence/source-E01-new.json
```

3. 보고서의 candidate_snapshot에 있는 보관본을 직접 읽는다. 문서 본문·필요한 절·적용 버전을 확인한다.
   로그인 화면·오류 페이지·본문 없는 JavaScript 셸이면 기준으로 지정하지 않는다.
4. 확인한 범위를 적어 기준을 지정한다.

```sh
python3 scripts/knowledge_sources.py pin --report knowledge/evidence/source-E01-new.json --source E01 --review-note '보관 본문과 적용할 절을 읽고 기존 설명을 대조한 결과 기록'
```

5. 연결된 주장·충돌·미결정을 대조하고 위키·목차·질문·이력을 갱신한다. 새 주장은 원본과 대조한
   평가 사례로 보강한다. 수집이나 pin 자체는 read 상태·위키 내용·플랫폼 준비 상태를 변경하지 않는다.
6. `python3 scripts/knowledge.py check`와 관련 검사를 실행한다.

## 변경 확인

같은 fetch 명령에 새로운 보고서 파일명을 지정하면 현재 기준과 새 응답의 정확한 바이트를 비교한다.
captured는 최초 수집, unchanged는 같은 바이트, changed는 변경 후보, unavailable은 수집 실패다.
종료 코드는 정상 수집/일치 0, 실패 포함 1, 실패 없이 변경 발견 2다. 기존 보고서는 덮어쓰지 않는다.

변경 후보는 새 파일로 보존하고, 보고서의 affected_documents에서 해당 출처를 직접 참조하는 위키를 찾는다.
실제 본문 차이와 관련 주장을 검토한 뒤 pin한다. HTML 장식만 바뀌어도 changed일 수 있으므로
바이트 변경만으로 기술 규칙이 바뀌었다고 판단하지 않는다. 간접 참조·평가·실행 근거도 별도로 점검한다.

pin은 보관 파일의 해시와 후보 생성 당시 기준을 확인하고 이전 기준·검토 이유를 이력에 보존한다.
다른 기준이 먼저 지정됐거나 보관 파일이 수정됐으면 거부한다. 실패한 수집을 기존 기준에 덮어씌우지 않는다.

`knowledge.py check`는 네트워크 없이 현재 지정한 보관본의 존재·크기·해시를 검사한다.
온라인 변경 확인은 fetch를 명시적으로 실행해야 한다. 예약 실행과 수집 결과의 자동 의미 검토는 아직 없다.
이전 기준을 유지한 상태에서 최신 문서와도 일치한다고 주장하지 않는다.

## 실제 수행한 범위

[최초 수집 K02](../../evidence/2026-10-28-sources-initial.json)에서 E01·E13·E19·E20·E26·E27·E28
7개를 수집했다. 보관본의 관련 절을 확인하고 기준 지정 이유를 sources.json에 기록했다.
[재조회 K03](../../evidence/2026-10-28-sources-verified.json)는 같은 7개 응답을 기준과 비교한 결과다.
이후 전체 패키지 구축에서 등록 외부 출처를 49개로 확장하고 모두 보관·확인 범위 기록·기준 지정을 마쳤다.
초기 7개와 이후 수집 이력은 보존하며 현재 상태는 [구축 현황](../../STATUS.md)을 따른다.

실제 수집과 별도로 격리된 합성 사례에서 변경 감지·실패 보존·기준 지정·오래된 후보 거부·파일 변조·경로 제한을
검사했다. 변경된 원문을 LLM이 자동 해석해 정확하게 수정하는 능력이나 개발 시간 절감은 검증하지 않았다.
질의는 [목차](../index.md)와 출처를 함께 읽고, 점검에서는 문서 간 모순·낡은 주장·누락된 연결도 확인한다.

이후 상세 언어/플랫폼 패키지 보강에서 E50–E63을 추가해 63개를 보관·검토했다.
E55의 첫 실패와 이전 경로의 redirect shell은 기록을 남겼으며, 본문이 있는 canonical 문서를 확인해 기준으로 지정했다.
수집 성공 상태만으로 실제 문서 본문을 읽었다고 판단하지 않는다.
`knowledge.py check`는 현재 언어 예제 파일·러너 해시도 DX09 실행 기록과 대조한다.
출처 해시만 갱신해 이전 예제 실행 결과를 최신 결과로 재사용할 수 없다.
