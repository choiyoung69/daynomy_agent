# 종목 검색과 가격 조회 이식 계획

이 문서는 [기존 동작](../projects/daynomy/stock-search-price.md)을 다섯 방식으로 옮기기 위한
설계 후보와 검증 항목이다. 대상 앱과 사용 버전은 아직 정하지 않았으며 플랫폼별 구현도 없다.

## 공통으로 유지할 동작

검색어·국가별 요청, 검색 대기·이전 요청 취소, 결과 없음·오류·로딩 구분,
선택 종목의 저장 종가와 기준일, 사용자가 입력한 단가 보존을 같은 시나리오로 확인한다.
UI의 모양과 OS 탐색 방식은 별도로 정하되 제품 규칙의 차이는 결정 기록으로 남긴다.

| 대상 | 조사할 대응 | 실제로 확인할 항목 |
| --- | --- | --- |
| Android 네이티브 | Kotlin과 Compose 후보, 검색 작업 취소와 화면 상태 관리 | 화면 재생성·이탈·복귀, 늦은 응답, 입력값 보존 |
| iOS 네이티브 | Swift와 SwiftUI 후보, 작업 취소와 화면 상태 관리 | 화면 이탈·복귀, 늦은 응답, 날짜와 숫자 디코딩 |
| React Native | TypeScript 로직의 브라우저 의존성 분리, 플랫폼별 코드 | DOM·window·저장소 대체, Android/iOS 각각의 입력·탐색 |
| Flutter | Dart로 모델·검증·상태 전환 대응 | 숫자 표현, 취소 후 상태 반영 방지, 위젯 이탈·복귀 |
| WebView | 기존 웹과 앱 호스트 연결 | 로그인·쿠키, 외부 링크, 뒤로 가기, 키보드, 호스트 연결 |

위 대응은 제안이며 검증된 라이브러리 선택이나 자동 변환 규칙이 아니다.
React Native의 플랫폼별 분기는 E02, Dart 실행 대상별 숫자 차이는 E03,
Android WebView 탐색·JavaScript 연결은 E04를 참고한다. Android 문서를 iOS 보장의 근거로 쓰지 않는다.
Swift·Kotlin의 구체적인 API 선택은 [자료 안내](../shared/reading-list.md)의 공식 문서에서 추가 조사한다.

## 시간 단축을 위한 공통 준비

사용자 목표에 따라 검색·종가 API 계약, 화면 상태와 오류 규칙, 공통 시나리오·입력/기대값을
한 번 준비해 다섯 대상에 전달한다. 디자인 자산과 플랫폼 의존성이 없는 기존 로직은 재사용 가능성을 먼저 확인한다.
각 대상은 공통 근거와 자기 플랫폼의 차이만 읽고 구현할 수 있게 문서를 연결한다.

계약과 환경이 준비되면 독립 대상의 구현·검증 작업을 병렬 배정할 수 있다.
공통 계약 변경이나 공유 검사는 조정하며, 최초 실행 시점과 최종 검증 완료 시점을 따로 측정한다.
실제 배정과 효과 측정은 아직 없으며 [시간 측정 계획](../../evals/README.md)을 따른다.

## 먼저 만들 재현 사례

1. `삼성`, 공백, 특수문자와 KR/US 검색어를 같은 API 요청으로 만들 수 있는지 확인한다.
2. A 검색의 응답을 지연하고 B를 먼저 응답시켜 최종 목록이 B인지 검사한다.
3. 종가 요청 중 단가를 직접 입력한 뒤 응답을 완료해 입력값이 유지되는지 검사한다.
4. 가격 없음·가격 타입 오류·0 이하 가격의 API/화면 처리 층을 구별한다.
5. 휴일 기준일과 시간대 경계에서 baseDate의 달력 날짜가 유지되는지 검사한다.
6. 큰 정수 ID와 소수 가격을 원시 JSON → 디코딩 → 계산 → 표시로 연결해 비교한다.

각 사례에 원본/대상 버전, 입력, 기대값, 실제값, 명령과 결과를 남긴다.
반올림·새 인증 방식 등 현행 동작을 바꾸는 선택은 원본과의 차이로 명시한다.
현재 재현 사례는 계획이며 실행 결과가 아니다. [질문 목록](../../questions.md)의 Q01–Q05와 연결된다.
