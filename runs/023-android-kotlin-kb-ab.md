# 023 — Android/Kotlin KB 전달 범위의 실제 토큰 비교

- 날짜: 2026-11-04. [Issue #5](https://github.com/choiyoung69/daynomy_agent/issues/5).
- 기준 코드: `0efb8e24d3eb2610065d1f960bd2721b66fcb67b`. 기존 앱은 보존했다.
- 성격: 과거 검색어 소실 회귀를 구성한 격리 실험. 현재 제품의 새 결함 수정이나 실제 역사 소스의 재실행이 아니다.

## 결과

같은 시작 코드·요구사항·고정 테스트·모델에서 최소 KB 조건의 구현 토큰은 99,308개로 전체 KB 조건 136,463개보다 37,155개(27.23%) 적었다.
두 수정은 같은 한 줄이고 각각 기존 JVM 105개 테스트를 새로 실행해 통과했다. 한 번의 작고 명확한 회귀 수정 사례이므로 다른 기능·전체 개발·실제 청구 비용의 절감률로 일반화하지 않는다.

| 항목 | A: 기존 전체 조합 | B: 필요한 문서 선택 |
| --- | ---: | ---: |
| KB 문서 | 18 | 3 |
| KB 본문+선택 출력 문자 수 | 48,735 | 6,676 |
| 작업·코드·테스트 포함 입력 문자 수 | 60,808 | 18,749 |
| 미캐시 입력 토큰 | 24,974 | 6,575 |
| 캐시 입력 토큰 | 109,440 | 90,880 |
| 출력 토큰 | 2,049 | 1,853 |
| 총 토큰: 캐시 포함 | 136,463 | 99,308 |
| 모델 응답 수 | 3 | 3 |
| 구현 에이전트 턴 경과 | 48.847초 | 47.441초 |
| Gradle 자체 보고 경과 | 10초 | 10초 |
| 실제 JVM 검사 | 105 통과 / 0 실패 / 0 skip | 105 통과 / 0 실패 / 0 skip |

미캐시 입력 감소는 73.67%, 총 토큰 감소는 27.23%다. 캐시 입력은 총 토큰에 포함된다. 출력에 포함된 추론 토큰을 다시 더하지 않는다.
입력 문자 수는 토큰이 아니다. 위 토큰은 파일 크기 환산이 아니라 각 조건의 원본 token_usage_record 합계다. 초기 지침·도구 정의 등 에이전트의 공통 문맥도 포함돼 문서 크기 감소율과 일치하지 않는다.
모델/추론은 실제 로그에서도 두 조건 모두 gpt-6.1-sol / medium으로 확인했다. 새 문맥 fork_turns=none으로 실행했고 다른 조건의 결과를 입력하지 않았다.

## 왜 이 작업을 골랐나

독립 기준 검토에서 MarketController의 수동 단가·검색어 보존은 이미 구현/테스트돼 있음을 확인했다.
과거 review-initial.md R1과 review-regression-red.json에는 clearSelection에서 query를 지워 검색어가 사라졌던 결함이 남아 있다.
이 근거로 현재 코드의 격리 복사본에 query 초기화 한 항목만 다시 넣었다. [입력 구성 diff](../experiments/android-kb-ab/historical-input.diff)는 의도적인 실패 구성이다.
이를 제품에 반영하지 않고 두 구현자가 각각 고치도록 했다. 원본에 없던 버그를 실제 제품 결함으로 보고하지 않는다.

## 고정 기준과 실행

1. 독립 기준 검토자가 원본 웹의 종목 변경 handler·기존 Android 계약/테스트와 현재 코드를 대조했다.
2. 기존 MarketControllerRegressionTest를 수정 없이 실행했다. 3개 중 검색어 보존 1개만 기대값과 달라 실패했다. 의도한 red다.
3. 같은 Kotlin 소스·모델 타입·회귀 테스트·요구사항을 두 조건에 제공했다. A는 context --require-ready의 18개 문서, B는 기능+상태/탐색+비동기/취소 3개다.
4. 큰 도구 출력이 모델에게 잘리는 문제를 피하려고 최종 유효 쌍은 두 조건 모두 입력을 8개 작은 블록으로 나누고 한 번의 읽기 도구 호출에서 별도 결과로 전달했다.
5. 로컬 실행 로그의 읽기 결과 8개가 각각 해당 입력 파일과 일치함을 대조했고 두 구현자도 마지막 </Knowledge>까지 확인했다.
6. 구현자는 입력만 읽고 수정 소스를 반환했다. 빌드·테스트는 조정자가 격리 프로젝트에서 실행했다. 구현자 자신의 테스트 통과 주장을 근거로 사용하지 않았다.
7. A/B 각각 :market-core:test를 실행했다. 로그는 양쪽 모두 4 actionable tasks: 4 executed이며 이전 XML·UP-TO-DATE 통과를 새 실행으로 세지 않았다.
8. 기존 테스트 파일 14개의 해시와 모든 구현 diff를 대조했다. 테스트는 동일하고 A/B 수정은 일치하며 원본 앱 해시도 그대로다.

## 성공한 두 조건 외에 실제로 든 비용

준비·실패를 성공한 쌍의 절감률에 감추면 안 된다. 아래는 같은 작업에서 실제 추가로 측정한 에이전트 사용량이다.

| 구간 | 총 토큰: 캐시 포함 | 처리 |
| --- | ---: | --- |
| 독립 대상/계약 조사 | 558,633 | 공통 준비 |
| 초기 B 구현 | 99,064 | 전달 불완전 쌍/전달 실패로 효과 비교에서 제외 |
| 초기 A 구현 | 111,352 | 전달 불완전 쌍/전달 실패로 효과 비교에서 제외 |
| 전달 확인 A 재시도 | 69,799 | 전달 불완전 쌍/전달 실패로 효과 비교에서 제외 |
| 위 구간 합계 | 838,848 | 실제 추가 사용량이며 0으로 취급하지 않음 |

- CLI 첫 호출은 현재 ChatGPT 로그인에서 지정 모델을 지원하지 않는다는 오류로 3.111초 만에 거절됐다. 사용량 이벤트가 없어 토큰 0이라고 단정하지 않는다. 같은 호출을 자동 재시도하지 않고 앱 경로로 전환했다.
- 초기 A는 도구 출력이 잘렸다고 보고해 그 쌍을 제외했다. 출력 한도를 늘린 후속 A도 모델이 잘림을 보고하고 중단했다. 원본 보관 로그에는 전체 결과가 남아 있었으나 모델에게 보인 범위와 동일하다고 가정하지 않았다.
- 원인을 다시 검토해 8개 개별 출력 블록으로 전달을 고정한 최종 한 쌍을 사용했다. 이 전달 절차를 통과한 뒤 추가 성공 쌍을 반복 실행하지 않았다.
- 독립 최종 검토가 승인했다. 추가 사용량은 총 253,678토큰이며 공개 집계에 별도로 기록했다. 조정자는 14개 테스트 파일 해시를 대조했고, 독립 검토자는 핵심 회귀 파일의 해시와 실행된 전체 suite를 확인했다. [독립 검토](../experiments/android-kb-ab/validation.json).
- 이번에 측정한 하위 에이전트 전체 합은 1,328,297토큰이다. 현재 조정 채팅의 사용량은 턴 종료 전 확정하지 못해 포함하지 않았으며 0도 아니다.
- 따라서 27.23%는 구현 구간의 관측 차이다. 이번 실험 전체가 단일 구현보다 저렴했다는 주장이 아니며, 준비·제외 실행 비용이 더 컸다.

## 한계와 다음 적용

- 단일하고 쉬운 한 줄 회귀다. 작업 설명과 테스트에 요구사항이 충분히 담겨 있어 긴 KB의 효용이 낮았을 수 있다.
- A→B 순서로 한 번 실행했다. 무작위 순서·교차 반복이 없고 캐시 상태/호스트 부하는 같다고 보장하지 않는다.
- 읽기 블록 수는 같지만 답변 파일을 쓰는 도구 선택은 달랐다. 이는 기록된 모델 동작이며 완전히 동일한 도구 경로 실험은 아니다.
- 두 JVM 검사의 의존성 캐시는 red 준비에서 데워졌다. A 검증이 B의 원격 모델 작업과 겹쳤으므로 작은 시간 차이를 성능 개선으로 해석하지 않는다.
- APK·에뮬레이터·화면·HTTP/DB는 실행하지 않았다. 이 실험은 그 영역의 완료/호환을 주장하지 않는다.
- 기존 전체 context와 3문서 패킷의 정보 범위가 다르다. 임의의 Android 작업을 3문서만으로 처리해도 된다는 결론은 아니다.
- 현재 packs.json·knowledge.py의 기본 조합, DB 잠금·재시도·전체 하네스는 바꾸지 않았다. 과거 보고서의 세 병목을 모두 해결한 상태도 아니다.

다음 실제 구현에서는 질문/기능별 필요한 규칙과 문서를 먼저 명시하고 준비·전달 크기·사용량·확인 결과를 연결한다.
전달 잘림 감지를 사전 확인하고 같은 실험의 준비를 반복하지 않는 것이 이번에 드러난 추가 개선점이다.
상태/검색어 회귀에 대한 3문서 조합은 재사용 후보로 유지하되 인증·거래·금액 정책 변경에는 관련 계약과 추가 지식을 포함한다.
