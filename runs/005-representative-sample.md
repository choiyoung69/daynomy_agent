# 005 — 세 API 실제 재현과 AI 구조 확인

- 날짜: 2026-10-21 KST. 요청: 몇 개 기능을 실제로 재현하고 현재 AI 구조와 시간을 확인한다.
- 대상: 뉴스 목록 GET /api/news, 뉴스 상세 GET /api/news/{id}, 평가 계산 POST /api/portfolio/calculate.
- 기능 코드: [실험 크레이트](../experiments/representative/README.md). 기존 app/ 피드백 앱과 분리했다.
- 실제 비교: **최종 44/44 통과**, fmt·Clippy·빌드 성공. 원본 Spring 전체 앱과 Rust 서버가 같은 새 fixture DB를 조회했다.
- 원본 backend 474개 파일의 원본/실행 복사본 해시 일치. 이전에 만든 동일 원본 jar를 재사용했다.
- 자동 CLI 실험은 중간 오류·429로 blocked였다. 대화 Codex의 별도 보완을 거쳐 실제 비교가 통과했다.
  자동 CLI 조정기만으로 전 과정을 완료했다고 주장하지 않는다. 최종 별도 리뷰 판정은 아래에 기록한다.

## 무엇을 재현했나

뉴스의 공개/비공개 구분·카테고리·페이지·정렬·상세·이미지/출처와,
계산의 원화/달러·정확한 십진수·혼합 날짜·가격 없음·최대 수량·최소/최대 평균가·입력 오류를 비교했다.
추가로 빈 query 값, 지수 숫자 1e2/1e100/1e-100/0e100, 실제 DB 변경 반영과 조회 DB 불변성을 확인했다.
JSON 필드를 통째로 지우거나 오류를 무시하지 않았다. 숫자 표현·같은 Instant·키/오류 배열 순서만 정규화했다.

신뢰된 HTTP/CSRF/DB 어댑터는 대화 Codex가 준비했다. news.rs와 portfolio_calc.rs는
실제 CLI 구현 역할이 처음 작성했고, 이후 실제 검토 피드백과 대화 Codex 보완을 거쳤다.
어댑터의 테이블 전수 로딩은 작은 fixture 목적이며 운영 쿼리/성능 구현이 아니다.
기능 속 AI 분석 호출, 로그인, 매수·매도 저장, 외부 실제 환율 조회, 전체 기능/배포는 이번 실험에 없다.

측정 시작 이전의 원본 분석·명세·샘플 실행기 준비 시간은 위 호출 시간에 포함하지 않았다.
전체 사용자 요청 처리 시간을 위 2분 42초로 표현하지 않는다. 이번은 기존 Rust 의존성 캐시와
이미 빌드한 Spring 원본이 있는 환경이었다. 빈 환경의 설치/최초 빌드 시간과 다르다.
동일 코드의 이후 재실행도 처음부터 구현한 실험과 구분해야 한다.

각 호출/검사의 원시 측정은 state.json의 measurements에 UTC 시각과 perf_counter 초 단위로 남겼다.
아래 두 자동 실험과 별도 보완 실행은 결과를 서로 덮지 않고 보존했다.

## 실패 → 수정 기록

1. **코드 문법 오류**: 첫 구현의 구조체 리터럴 괄호 누락을 rustfmt가 거절했다.
   별도 검토가 위치를 지적하고 다음 구현에 자동 전달했다.
2. **Clippy 오류**: map_or, 올림 나눗셈, 불필요한 unwrap 5건을 거절했다. 경고를 허용하도록 낮추지 않았다.
3. **검사기 오류**: 같은 Instant의 UTC/+09:00을 다르게 판단했다. 비교기를 UTC 정규화로 고치고
   같은/다른 Instant 및 큰 십진수 기록·배열/필드 누락을 구분하는 회귀 테스트 5개를 추가했다.
4. **실제 계산 오류**: 큰 금액에서 `(n*d).signum()` 중간 곱셈이 overflow했다. CLI 수정 후 35개가 통과했다.
5. **검사 통과 후 독립 리뷰 지적**: 1e2 JSON 숫자, 빈 page/size/category, 1e100의 DTO 오류 분류가 달랐다.
   테스트 35개를 통과해도 승인되지 않았고, 검토 피드백으로 후속 수정이 진행됐다.
6. **429 중단**: 최대 3회 수정/제한된 전송 재시도를 지켰다. 다음 구현이 429 3회로 실패한 뒤
   자동 실험은 blocked로 남겼다. 대화 Codex가 별도 복사본에서 보완했고 42개 실제 비교가 통과했다.
7. **42개 통과 후 독립 리뷰 지적**: i64::MAX 수량·최대 평균가 조합에서 추가 10^4 배율이 overflow할 수 있었다.
   대화 Codex가 몫·나머지 장제법으로 바꾸고 최대 수량·최소 평균가 사례를 추가했다. 최종 비교는 44/44다.
8. **리뷰 출력 형식 거절**: 승인 응답이 긍정 관찰을 findings에 넣어 검증기가 거절했다.
   approve는 findings/questions가 비어야 한다는 조건을 유지하고 별도 재검토를 요청했다.

처음에 빠르게 생긴 코드가 바로 검증 완료였다는 결론을 내리지 않는다.
검사도 AI가 작성하므로 검사기의 버그와 구현의 버그를 구별해야 한다.

## 현재 AI 구조

| 구성 | 실제 역할 | 권한/실행 |

| CLI 검토 역할 | 원본·명세·코드·실제 검사 증거를 읽고 승인/수정 요청 | 매 호출 새 세션, 도구 파일 읽기 전용. |
| Python 조정기/검사기 | 순서·반복 제한·상태·해시·명령 실행·실제 비교·측정 | AI가 아니다. 승인과 검사 결과가 모두 있어야 완료. |

원래 피드백 조정기는 scripts/agent_workflow.py, 이번 샘플 조정기는 scripts/sample_features.py다.
둘 다 같은 CLI 어댑터를 사용한다. sample_feature_gate.py는 이번 샘플의 새 검사기다.
실제 프로그램 호출 방식은 codex exec --ephemeral --json --output-schema이며 결과 JSON과 thread.started 세션 ID를 보존한다.
모델명은 명시 고정하지 않았다. CLI 기본 선택을 쓰며 데스크톱 대화의 모델명과 같다고 추측하지 않는다.

**현재는 구현 → 검사 → 검토 → 수정의 순차 구조다.** 기능별 병렬 구현 큐, 파일 충돌 조정,
상시 예약 실행, 호출 공급자 변경, 자동 서비스 복구 재개는 없다.
과거 하네스 제작에 쓴 보조 에이전트 2개는 완료 상태이며 이번 구현 호출 수에 포함하지 않았다.
서버/테스트 프로그램을 AI 수에 포함하지 않는다. 이번에는 역할 2종을 필요할 때 새 세션으로 호출했다.

도구 쓰기 제한은 실제 OS probe로 확인했다. 파일 읽기·서버 네트워크·DB 사용자 권한을
완전히 격리한 적대적 코드 환경은 아니다. 사용자 승인 후 필요한 샘플 코드·명세·원본 일부·검사 결과를 Codex로 전송했다.
첫 전송은 자동 승인 검토가 이전 승인은 피드백에 한정됐다고 차단했고, 새 범위에 대한 명시적 승인을 받은 뒤 실행했다.

## 검증과 다음 판단

- fmt·Clippy·Rust 빌드, 실제 Spring/Rust HTTP/DB 44개 통과.
- 비교기 회귀 테스트 5개·기존 조정기 테스트 39개 통과.
- 기존 app/ Rust 소스는 그대로다. 전체 기능 이식·배포 또는 자동 CLI 전체 성공으로 보고하지 않는다.
- 3개 API의 관찰을 81개 API로 단순 곱하지 않는다. 인증·거래 원장·외부 실제 API·운영 검증이 빠져 있다.
- 병목은 처음 코드 생성만이 아니라 입력/숫자 의미·검증기 오류·리뷰 피드백·429 대기였다.
