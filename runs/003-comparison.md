# 003 — 원본 Spring과 Rust의 피드백 비교

- 날짜: 2026-10-21 KST.
- 목적: 명세에서 추출한 동작이 원본 실서버와도 같은지 실제 요청·DB로 확인한다.
- 작업자: 현재 대화의 에이전트 1개. 독립 리뷰·병렬 에이전트는 사용하지 않았다.
- 상태: 두 번 실행 완료, 같은 결과 재현. 기존 계약 일치, 미확정 입력에서 차이 3개 확인.
- 원본 앱: Spring Boot 4.1.0, Gradle 9.5.1, JDK 21. PostgreSQL 18 전용 테스트 환경.

## 실험 조건과 근거

원본의 빌드 파일·Gradle wrapper·src/main 474개 파일을 `.local/spring-reference`에 복사했다.
빌드와 실행 전후 원본 및 복사본의 SHA-256이 모두 동일함을 확인했다.
선택한 원본 29개 파일의 기존 preflight도 통과했다.

전체 소스 목록은 `.local/comparison/source-snapshot.json`에 있다.
첫 실행 목록 파일 SHA-256:
`20591c293cfb8f048d7226cbf94032e09c5ef6bc77e7a9800a217a5521f74544`.

원본 애플리케이션 전체를 실제 HTTP 서버로 시작했다. MockMvc나 필터를 끈 테스트가 아니다.
원본 피드백·검증·보안·오류 처리 코드는 수정하지 않았다.
운영 환경과의 차이는 별도 properties 설정·환경변수에 두었다:

- 로컬 바인딩, 전용 DB, 스케줄러 off, 외부 API 주소를 로컬 미사용 주소로 변경.
- OAuth·AWS 등에 테스트 전용 설정 사용. 원본 .env와 사용자 API 키 미사용.
- Spring과 Rust는 각각 18082·18083, DB는 각각 별도의 `_compare_test` 이름.
- Spring은 전체 앱의 JPA 검증을 위해 원본 51개 마이그레이션을 v53까지 실행.
  빈 Spring 비교 DB만 대상이며 Rust/기존 실험 DB에는 실행하지 않았다.

## 비교 판단

HTTP 상태·미디어 타입·JSON 값·저장된 내용·상태·행 수를 비교한다.
JSON 키/오류 배열 순서만 정규화하며, 생성 ID·시각·CSRF 토큰의 실제 값은 같을 필요가 없다.
기존 계약 사례에는 각 서버의 기대 HTTP 응답과 실제 DB 효과 검사도 함께 적용한다.
두 서버가 같은 잘못된 결과를 내도 계약 검사가 실패해야 한다.

비교기 자체 테스트는 잘못된 저장, 응답 본문 차이, 오류 항목 중복·추가 필드,
생성값 정규화, ID·시각 누락을 놓치지 않는지 확인한다.
이번 작업에서는 Rust 구현이나 기존 33개 인수 사례의 기준을 수정하지 않았다.

## 첫 실제 실행 결과

- HTTP 비교 구간: 2026-10-21 00:10:21–00:10:26 KST. 전체 준비·개발 시간은 아니다.
- 원시 보고서: `runs/comparison-20261020T151026581438Z.json` (파일명 UTC).
- 명세 사례 33개 + CSRF 준비 1개: **34/34 일치, 양쪽 모두 계약 충족**.
- 추가 관찰 7개: **4개 일치, 3개 차이**.
- 전체 명령 종료 코드: **1**. 비교는 완료됐지만 전체 호환 성공은 아니다.
- 데이터: Spring 비교 DB 14행, Rust 비교 DB 11행. 차이 3건은 Spring만 저장한 결과다.
- 두 서버와 이번 명령이 시작한 전용 DB 정상 종료, 데이터 보존.

| 사례 | Spring | Rust | 판단 |
| --- | --- | --- | --- |
| 정상·공백 정리·최대 길이·중복 요청 | 204, 계약대로 저장 | 동일 | 일치 |
| 빈 값·누락·길이 초과·잘못된 JSON | 400, 저장 없음 | 동일 | 일치 |
| CSRF 없음·불일치·쿠키/헤더 단독 | 403, 저장 없음 | 동일 | 일치 |
| content가 숫자 | 204, 한 행 저장 | 400, 저장 없음 | 차이 |
| content가 boolean | 204, 한 행 저장 | 400, 저장 없음 | 차이 |
| content 키가 중복된 JSON | 204, 한 행 저장 | 400, 저장 없음 | 차이 |
| 알 수 없는 필드 추가 | 204, 저장 내용 동일 | 동일 | 이번 사례 일치 |
| JSON 문서 뒤 추가 JSON | 400, 저장 없음 | 동일 | 이번 사례 일치 |
| 문서 전체 null/배열 | 400, 저장 없음 | 동일 | 이번 사례 일치 |

차이 3건은 기존 명세가 미확정으로 남겨둔 JSON 변환·중복 키 처리 영역이다.
원본 호환을 위해 Rust가 이를 허용할지, 엄격한 문자열 계약을 유지할지는 별도 결정이다.
이번 요청은 비교이므로 어느 쪽으로도 임의 변경하지 않았다.

## 한계

- 이것은 선택한 피드백 입력·CSRF 흐름의 HTTP/DB 비교다. 전체 Spring 테스트나
  다른 API·로그인·배포·성능·복구의 검증이 아니다.
- 쿠키 속성 전체, 모든 응답 헤더, 브라우저 CORS, 모든 Unicode/JSON 입력을 비교하지 않았다.
- 재시작·장애 검사는 이전 Rust 실험에서 수행했다. 이번에는 두 서버의 장애 동작을
  나란히 비교하지 않았다.
- 라이브러리/원본 소스가 바뀌면 결과가 달라질 수 있다. 재실행 결과와 소스 해시를 함께 본다.
- 스케줄러 off와 외부 주소 대체는 실행 설정이다. OS 수준의 외부 네트워크 차단을
  구축한 것으로 해석하지 않는다.

## 사용자 정책 확정 및 재검증 — 2026-10-21

사용자가 “피드백 내용은 문자열만 받고, 중복 키는 거절”로 결정했다.
앞선 종료 1의 결과는 당시 관찰로 보존한다. 이번 변경은 원본과의 차이를 없애는 것이 아니라,
원본과 다른 Rust의 목표 동작을 명시하고 엄격하게 검증하는 작업이다.

- 검증 관찰 구간: 00:21:04–00:26:02 KST (문서 작성·전체 대화 시간은 아님).
- 상태: 새 정책 구현 및 전체 로컬 검증 완료. 서버·이번에 시작한 DB 종료, 테스트 데이터 보존.
- 정책 범위: content의 숫자·boolean·배열·객체는 400/미저장, 문자열은 기존 검증 적용.
  같은 JSON 객체의 중복 키는 같은 값이어도 거절한다. unknown/nested/escaped key도 포함한다.
  서로 다른 객체의 동일 키와 중복 없는 unknown field는 허용한다.

### 무엇을 바꿨나

1. 명세에 원본 근거와 구별되는 사용자 결정으로 정책과 오류 응답을 명시했다.
2. 기존 Rust는 비문자열과 알려진 DTO 필드 중복을 이미 거절했다.
   unknown field와 중첩 객체의 중복까지 막기 위해 JSON을 순회하는 검사를 추가했다.
   일반 맵으로 변환해 중복 키가 덮어써지기 전에 탐지하며 새 의존성은 추가하지 않았다.
3. Rust 함수 테스트에 비문자열 거절·문자열 허용, 중복 키의 여러 형태,
   서로 다른 객체에서 재사용한 키의 허용을 추가했다.
4. 기존 HTTP/DB 인수 검증 사례는 유지하고 문자열 타입 및 중복 키 사례를 추가했다.
   중복 키 입력은 딕셔너리가 아닌 원시 JSON bytes로 보내 테스트에서도 중복이 사라지지 않게 했다.
5. 원본 비교에서 8개 정책 사례를 별도 분류했다. Spring은 기대한 204와 정확한 저장값/행 수,
   Rust는 기대한 400 오류 본문과 DB 무변경을 모두 확인해야 EXPECTED_DIFFERENCE다.
   승인된 사례라도 Rust가 저장하거나 Spring이 다른 값을 저장하면 실패한다.
6. 비교기 자체 회귀 테스트로 위 실패 탐지를 확인했고, `check.py verify`에도 연결했다.
