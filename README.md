# DAYNOMY Rust 에이전트 실험

기존 Spring 서비스의 비회원 피드백으로 시작해, 리그를 제외한 Rust 백엔드를 구현하는 프로젝트다.
현재 완료 상태·코드 위치·에이전트 구조·남은 작업은 [인계 문서](runs/010-three-hour-service.md)에 정리한다.
실행은 [Rust 백엔드 안내](app/README.md), 요구사항은 [전체 명세](spec/service.md)를 본다.
전체 서비스의 운영 배포가 완료된 것은 아니다.

초기 피드백·대표 기능·종가·작업 큐 실험은 `runs/001`–`009`의 과거 기록이다.

## 처음에는 이것만 읽기

리그를 제외한 전체 백엔드의 기능 범위·API·완료 기준은 [전체 기능 명세](spec/service.md)에 있다.
현재 상태는 범위 내 백엔드 코드 구현과 정해 둔 로컬 검사 통과다. 실제 외부 서비스 통합과 운영 검증은 남아 있다.

1. **무엇을 만들어야 하나?** → [전체 명세](spec/service.md)의 기능별 계약. 피드백의 상세 정책은 [피드백 명세](spec/feedback.md).
2. **실제로 어떻게 실행하나?** → [실행 안내](app/README.md)의 실행 절차.
3. **어디까지 확인했나?** → [최신 실행 기록](runs/010-three-hour-service.md)의 결과와 남은 차이.

## 구현이 맞는지 확인하는 방법

검증은 **약속한 동작과 실제 실행 결과를 비교하는 일**이다.
예를 들어 정상 요청은 204 응답과 DB 한 행 추가를 모두 확인하고,
빈 내용은 400 응답과 DB 변화 없음을 모두 확인한다.

| 검사 | 확인하는 것 | 실행 위치 |
| --- | --- | --- |
| 준비 확인 | 분석한 원본이 그대로인지, 도구가 있는지 | `python3 scripts/check.py preflight` |
| Rust 검사와 함수 테스트 | 빌드, 코드 검사, 길이·공백·CSRF 등의 규칙 | 아래 `verify`에 포함 |
| HTTP/DB 검사 | 실제 요청의 응답과 실제 저장 결과 | 아래 `verify`에 포함 |
| 재시작·저장 장애 검사 | 재시작 후 데이터 유지, 저장 실패 시 500, 복구 | `python3 scripts/check_lifecycle.py` |
| 원본 비교 | 원본 Spring과 Rust의 실제 HTTP 응답·DB 변화 | `python3 scripts/run_comparison.py` |
| 원본 대조와 코드 리뷰 | 명세 해석, 검사 누락, unsafe·의존성 등 | 원본·명세·코드를 읽고 확인 |

전체 백엔드는 [실행 안내](app/README.md)의 `service_gate.py` 예시로 검사한다.
아래는 기존 피드백 회귀 검사다. 같은 안내로 전용 DB와 서버를 시작하고,
서버와 같은 DB·인증 환경 변수를 설정한 터미널에서 실행한다.

```sh
export PILOT_BASE_URL=http://127.0.0.1:18081
export PILOT_TEST_DB_URL="$DATABASE_URL"
python3 scripts/check.py verify
python3 scripts/check_lifecycle.py
```

두 검사는 차례로 실행한다. `verify`는 포맷·clippy·Rust 테스트·빌드·검증기 자체
테스트·HTTP/DB 검사를 실행한다. `preflight`만 통과한 것은 기능 검증이 아니다.
테스트는 성공 요청으로 전용 DB에 데이터를 추가한다.

## 현재 검증의 의미와 한계

첫 구현에서 Rust 테스트 7개, 검증기 자체 테스트 9개,
HTTP/DB 사례 33개와 CSRF 준비 검사, 재시작·장애 검사 4개가 통과했다.
이는 [첫 구현 기록](runs/002-implementation.md)에 남긴 당시 결과다.

같은 에이전트가 명세·구현·테스트를 작성하고 리뷰했다. 같은 오해가 모두에 들어가면
테스트도 통과할 수 있다. 따라서 원본 근거와 기대 결과를 대조해야 한다.
2026-10-21 첫 원본 비교에서 기존 명세 34개 일치·추가 입력 3개 차이를 확인했다.
이후 사용자가 content는 문자열만 허용하고 중복 키는 거절하도록 확정했다.
정책 반영 후 Rust HTTP/DB 검사 46개 통과, 원본 비교는 공통 38개 일치·승인된 차이 8개
검증·추가 관찰 4개 일치로 종료 0이다. `full_match=false`로 의도적 차이는 계속 표시한다.
[비교 기록](runs/003-comparison.md)의 마지막 정책 변경 항목을 참고한다.
현재 자동 흐름에서는 별도 AI 검토를 실행한다. 전체 입력·운영 환경의 호환성을
보장한 것은 아니다. 최초 검증과 자동 작업의 실행 증거는 구분한다.

## 구현 → 검증 → 리뷰 → 수정 자동 실행

독립 기능의 병렬 실행은 아래 **뉴스·계산 병렬 실행**을 사용한다.
이 절의 `agent_workflow.py`는 기존 피드백 전용 순차 실행기다.

이 흐름에는 **AI 역할 두 개와 조정 프로그램 한 개**가 있다.
AI 역할은 실제 `codex exec`를 각각 새 문맥으로 실행한다. 같은 대화에서 역할 이름만
바꾸는 방식이 아니다. 조정 프로그램과 테스트 프로그램은 AI가 아니다.

| 담당 | 하는 일 | 쓸 수 있는 파일 |
| --- | --- | --- |
| 구현 에이전트 | 명세를 읽고 Rust 코드를 구현·수정 | 임시 작업 폴더의 Rust 파일 3개 |
| 검증 프로그램 | 포맷·빌드·테스트·실제 HTTP/DB·재시작·장애 검사 | 조정기가 관리하는 검사 결과 |
| 검토 에이전트 | 같은 코드와 검사 증거를 읽고 승인·수정 요청·결정 요청 | 읽기 전용 |
| 조정 프로그램 | 순서 연결, 권한 검사, 재시도, 완료 판정, 기록 | 별도 실행 폴더와 후보 코드 |

구현 에이전트의 “구현했다”는 보고만으로는 완료하지 않는다. 해당 코드의 실제 검사 성공,
별도 검토 승인, 검사·검토한 코드의 해시 일치가 모두 있어야 `completed`가 된다.
실패 원인과 리뷰 지적을 다음 구현 호출에 자동 전달하며 최대 3회까지 진행한다.
선후 관계가 있으므로 이 흐름 자체는 순차 실행한다. 서로 다른 모델 회사가 필수인 구조는 아니다.

로컬 Codex CLI 로그인(`codex login status`), Rust, PostgreSQL 도구와 `.local/cargo`의
기존 의존성 캐시가 필요하다. 별도 API 키를 코드에 넣지 않는다.

```sh
# 의도적인 “저장 없이 204 반환” 결함을 넣어 자동 발견·수정을 시험한다.
python3 scripts/agent_workflow.py --demo

# 확정한 피드백 명세에 대해 일반 작업을 실행한다.
python3 scripts/agent_workflow.py --task '승인된 피드백 명세에 맞게 구현하고 검토하라'
```

각 실행은 `.local/agent-workflows/<실행 ID>/`에 `state.json`, 역할별 결과·세션 ID,
명령 로그, 실제 검사 JSON, 검증한 소스, `candidate.patch`를 남긴다.
성공한 후보는 실행 폴더에 보관한다. 원래 `app/src/`에 자동 반영하거나 커밋하지 않는다.
피드백 명세·검사·Cargo 설정·마이그레이션은 고정한 복사본을 사용한다.
원본과 복사본의 해시, 가져올 파일 목록, 기존 Rust 테스트 유지, unsafe 금지 속성을 확인한다.
구현/검토 도구와 실행 서버·Rust 함수 테스트에는 OS 파일 쓰기 제한도 적용한다.

| 상태 | 뜻과 다음 행동 |
| --- | --- |
| `completed` / 종료 0 | 검사와 리뷰 승인. 후보와 패치를 확인한다. |
| `needs_decision` / 종료 3 | 정책을 임의로 정하지 않고 질문을 기록. 사람이 명세를 확정한 뒤 새 실행을 시작한다. |
| `failed` / 종료 2 | 최대 수정 횟수 내에 해결하지 못함. 기록으로 원인을 조사한다. |
| `blocked` / 종료 2 | 도구·권한·호출·기준 변조 등으로 검증 불가. 성공으로 계산하지 않는다. |

명시적인 429/503 호출 오류만 최대 3번 시도하며, 시도마다 원시 로그를 보존한다.
재시도 간격은 30초·60초다.
에이전트 호출당 240초, 검사 명령당 최대 600초 제한을 둔다. 무제한 재시도나
컴퓨터가 꺼진 뒤의 재개·예약 실행·전체 서비스 자동 구현은 포함하지 않는다.
읽기 권한·서버의 외부 통신·DB 사용자 권한을 완전히 격리한 적대적 코드 실행 환경은 아니다.
원본 비교 50개는 별도 `run_comparison.py`의 검사이며 매 수정 회차에 실행하지 않는다.

현재 실제 실험에서는 저장 누락 발견 → 별도 리뷰 지적 → 자동 수정 → HTTP/DB 46개와
장애 검사 4개 통과까지 확인했다. **수정 후 최종 AI 리뷰는 429로 막혀 전체 성공 시연은
미완료**다. 조정기는 `completed` 대신 `blocked`로 남겼다.
[실행 기록](runs/004-agent-workflow.md)에 실제 세션·실패와 미검증 항목을 구분했다.

## 뉴스·계산 병렬 실행

`scripts/parallel_features.py`는 두 구현 작업을 별도 폴더에서 동시에 실행한다.
작업·모델 설정은 [agents/representative.json](agents/representative.json)에 있다.
현재 모델 호출 도구는 Codex CLI이며, 직접 모델 API를 호출하는 실행기는 아니다.
구현 에이전트 2개는 각각 뉴스(`news.rs`)와 계산(`portfolio_calc.rs`)만 수정한다.
검토 역할은 매번 새 문맥으로 실행하며, 검토 슬롯은 1개다. 전체 모델 동시 호출은 최대 2개다.

```text
조정 프로그램
  ├─ 뉴스 구현 ── 검사 ── 독립 리뷰 ── 필요 시 수정
  └─ 계산 구현 ── 검사 ── 독립 리뷰 ── 필요 시 수정
                                  ↓ 두 작업 승인
                       승인 파일만 통합 → 실제 44개 검사
```

한 작업이 리뷰/수정 중이어도 다른 작업은 진행한다. 컴파일·검사 실패는 바로 구현 담당에게
전달하고 불필요한 리뷰 호출을 생략한다. 수정은 작업별 최대 3회다.
공유 포트·빌드 결과물·DB 시작/종료가 있어 실제 검사는 파일 잠금으로 한 번에 하나만 실행한다.
다른 `run_comparison.py`, 피드백 검사, DB 시작/종료 명령을 함께 실행하지 않는다.
작업별 44개 검사와 마지막 통합 44개 검사가 있으므로 전체 시간이 절반이라는 보장은 없다.

```sh
# 설정만 확인. 모델/DB 호출 없음.
python3 scripts/parallel_features.py --plan

# 현재 샘플에서 작업 2개를 병렬 실행하고 검사·리뷰·수정을 연결.
python3 scripts/parallel_features.py

# 각 담당 파일을 501 빈 구현으로 시작하는 실제 복구 실험.
python3 scripts/parallel_features.py --demo
```

에이전트별 `model`에 사용 가능한 모델 ID를 지정하거나 `--implementer-model` /
`--reviewer-model`로 지정한다. 설정의 `null`은 **CLI 기본 모델**이며 별도 모델을
배정했다고 주장하지 않는다. 실제 요청 설정·세션 ID·단계별 시간은 실행 기록에 남긴다.
동일 계정의 호출 제한을 공유한다. 병렬 버전은 429/503 발생 시 자동 재전송하지 않고
해당 작업을 `blocked`로 남겨 반복 호출을 줄인다. 독립적인 다른 작업은 계속한다.

결과는 `.local/parallel-features/<실행 ID>/state.json`, 작업별 후보·로그·리뷰,
`integrated/`, `candidate.patch`다. 미커밋 작업을 보존하기 위해 이번에는 Git worktree 대신
기준 코드의 독립 복사본을 쓴다. 성공한 파일을 원래 앱에 자동 반영하거나 커밋하지 않는다.
`--demo`의 새 구현 실험과 기존 코드로 실행한 검토 실험은 구분해야 한다.
합성 테스트는 `python3 scripts/test_parallel_features.py`이며 실제 모델/DB 성공의 근거는 아니다.
실제 실행 결과와 한계는 [병렬 실행 기록](runs/006-parallel-features.md)에 남긴다.
첫 실제 실행은 두 구현 호출이 약 53초 겹쳤고 계산 후보는 44개 실제 비교를 통과했다.
뉴스 Clippy 오류의 자동 수정 요청과 계산 리뷰 호출은 429로 막혀 전체는 `blocked`다.
실제 모델로 통합까지 성공했다고 보고하지 않는다.

## 현재 방식의 문제점

아래 8개는 사용자가 제기한 **개선 전 문제**를 보존한 목록이다.
피드백 기능의 구현·계약 검증 완료와 아래 하네스 개선의 완료는 구분한다.
이 목록을 추가한 것만으로 실행 구조나 권한이 개선된 것은 아니다.

1. **AGENTS.md의 규칙 상당수가 지시 단계에 머문다.**
   일부 기능·DB·unsafe 검사는 있지만, 작업 범위·명세/테스트 변경·완료 선언을 모두
   자동으로 검사하거나 차단하지는 않는다. 문서에 금지했다고 실제 쓰기 권한이 없어지는 것은 아니다.
2. **사람이 붙어서 후속 프롬프트를 계속 제공해야 한다.**
   사용자가 “이 문서가 부족하다”, “이 문제는 언제 고치나”, “다음에는 무엇을 하나”를
   직접 지적해야 진행 방향이 바뀌었다. 승인된 작업의 분석·구현·검증·리뷰·수정을
   이어주는 전체 조정 흐름과 상태 관리가 없다. 서버 실행·비교 같은 일부 스크립트만 자동화됐다.
3. **구현 담당과 검증·리뷰 담당이 분리되지 않았다.**
   같은 에이전트가 명세·구현·테스트·비교기를 작성했다. 같은 오해가 모두에 들어갈 수 있고,
   구현 담당이 기준과 결과 보고를 함께 바꿀 수 있다. 통과 주장을 뒷받침하는 실제 실행 증거와
   기준 변경 검토가 필요하다. 현재 독립 검토 에이전트나 테스트 쓰기 권한 분리는 없다.
4. **기준이 없거나 사람의 판단이 필요한 경우의 처리가 지시로만 남아 있다.**
   원본을 조사하고 질문하라는 규칙은 있지만, 미결정 사항을 근거·선택지·영향과 함께
   관리하거나 해당 결정을 기다리는 작업을 완료에서 제외하는 자동 상태 처리가 없다.
5. **원본 재현과 원하는 제품 동작을 구별해 판단해야 한다.**
   reference의 버그나 오래된 동작을 그대로 복제해도 사용자 의도에 맞는다고 할 수 없다.
   원본 근거, 사용자 결정, 의도적인 호환 차이, 미확인 영역을 명세와 검증에서 구분해야 한다.
   피드백 입력 정책에는 이를 적용했지만 다른 기능까지 해결한 것은 아니다.
6. **여러 AI 에이전트가 협업하는 실행 시스템은 아직 구축하지 않았다.**
   현재는 대화의 Codex 작업자 하나와 테스트 프로그램이다. 구현·검토 담당이 별도 문맥과
   도구 권한으로 실행되고 결과를 주고받는 구조나, 실패 시 자동 재작업을 배분하는 조정기는 없다.
   역할 이름을 문서에 적거나 Python 테스트를 실행하는 것만으로 여러 에이전트가 생기지는 않는다.
7. **문서가 많아 목적과 현재 상태를 이해하기 어려웠다.**
   README에 문서 안내를 모았지만, 문서의 추가·중복·오래된 상태를 사람이 계속 지적해야 하는
   부담은 남아 있다. 모든 기능의 세부 지시서를 미리 늘리기보다 필요한 명세와 증거를 유지해야 한다.
8. **기능 완료와 개발 체계의 개선 완료가 혼동됐다.**
   피드백 테스트가 통과한 뒤 사용자가 지적한 하네스 문제를 해결하기 전에 다음 기능으로
   넘어가자는 제안이 나왔다. 앞으로는 기능 결과, 하네스의 미해결 문제, 다음 개선을 별도로 보고해야 한다.

현재 보완한 부분과 남은 부분:

### 이 문제를 보완하는 순서

1. **구현과 완료 판정을 분리한다.** 구현 담당·별도 검토 담당의 입력/출력과 파일 권한을
   정하고, 승인된 기준의 변경 여부와 실제 검사 결과로 완료를 판정한다.
   현재 대화의 파일 권한과 별도로, 자동 실행 역할에 도구 권한 제한을 적용한다.
2. **작업을 이어주는 조정 프로그램을 만든다.** 구현 → 자동 검사 → 별도 AI 검토 → 필요한
   수정으로 이어지게 하고, 제한된 재시도와 사람의 결정 대기 상태를 관리한다.
   제품 정책이 미정인 부분은 질문하되 독립적으로 진행 가능한 작업은 계속한다.
3. **피드백 기능으로 이 구조를 검증한다.** 별도 복사본에서 잘못된 성공 응답·저장 누락·
   테스트 기준 변경·미실행 검사·미결정 정책을 주입해 실제로 실패나 결정 대기로 처리하는지 확인한다.
   테스트 통과나 역할 문서 존재만으로 에이전트 협업 체계가 작동한다고 보고하지 않는다.
4. **그다음 핵심 기능에 적용한다.** 새 기능은 명세·완료 기준부터 확정하고 같은 실행 흐름을
   반복한다. 병렬 실행은 담당 파일과 의존 관계가 나뉘는 작업에 적용한다.

### 2차 개선 방향

2026-10-21 기준. 현재는 **기능별로 역할 분리와 검증을 실험한 단계**다.
전체 서비스에 재사용할 공통 실행기, 안정적인 무인 실행, 개발 속도 개선까지 검증한 상태는 아니다.
아래 개선안은 다음 작업의 계획이며, 이 문서를 작성하면서 실행 구조를 추가 구현한 것은 아니다.

프로그램이 담당한다. 테스트 작성 역할을 기존 뉴스/계산 병렬 실행기에 연결한 것은 아니다.

에이전트는 이름·역할 지시·별도 실행 문맥·담당 파일·권한·결과 기록으로 구분한다.
현재 설정의 모델은 모두 `null`이며 CLI 기본 선택 또는 앱 모델 상속이다.

| 3 | 관련 API를 기능 단위로 묶고 검사 단계를 조정 | 수정 중 빠른 컴파일/단위 검사, 준비된 기능 묶음에 실제 비교·최종 리뷰 수행. 기존 완료 기준 유지. 결함 주입은 검사기/기준 변경 때 회귀 검증 |
| 4 | 시간·실패·변경·결과 보고를 실행 기록에서 자동 생성 | API마다 긴 문서를 수동 작성하지 않고 실행기가 측정 범위·사람 개입·미확인 항목을 포함한 요약 생성 |
| 5 | 같은 조건으로 관련 API 2~3개를 실행해 개선 전후 비교 | 준비/모델 호출/빌드/실제 비교/리뷰/대기를 분리 측정하고 검증 완료까지의 시간과 실패·수동 개입 횟수로 평가 |

다음 실험에서 새 API인지 기존 코드 재사용인지, 검사 범위와 모델/실행 경로가 같은지를 함께
기록한다. 빠르게 끝난 실패 실행을 성공 시간으로 세지 않는다. 에이전트 수 증가나 단일 재실행
시간만으로 속도 향상을 주장하지 않는다. 명세의 미결정 정책과 별도 전송 승인은 자동 추측으로 대체하지 않는다.

## 문서 유지 원칙

- 동작 변경은 명세, 실행법 변경은 앱 README, 작업 규칙 변경은 AGENTS.md에 반영한다.
- 과거 실험 기록은 당시 증거로 보존한다. 새 실험 결과를 과거 성공 결과에 덮어쓰지 않는다.
- 새 문서를 만들기 전에 기존 문서에 해당 내용을 둘 자리가 있는지 먼저 확인한다.
- `reference/`는 분석용 원본, `app/`은 구현, `scripts/`는 실행·검사 프로그램이다.
  테스트 프로그램은 AI 에이전트가 아니다.
