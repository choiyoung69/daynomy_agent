# 같은 근거를 본문과 파일로 전달한 실제 구현 비교

Issue #13 / PR #14. 기존 Android KB A/B의 격리 회귀 복사본과 CliAgent를 재사용했다. 새 실행기는 만들지 않았다. 두 조건 모두 같은 3문서 KB·시작 코드·계약·요청 모델 gpt-6.1-sol / medium·고정 JVM 검사를 사용했다. 본문 전달(A)과 실제 Workflow.prompt의 근거 파일 참조(B)만 비교했다. 각 새 세션 1회, timeout 120초, max_attempts 1. 원본 앱은 변경하지 않았다.

회귀 RED는 3개 중 1개 실패. 구현 후 A/B 모두 동일한 한 줄 수정으로 고정 JVM 105개 통과, skip/실패/검사 파일 변경 없음. B의 실제 근거 파일 읽기도 CLI 명령 로그에서 확인했다. A.diff/B.diff와 results.json을 참조한다.

| 조건 | prompt bytes | agent 실행 | 캐시 입력 | 비캐시 입력 | 출력 | 총 토큰 | shell 명령 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| A 본문 | 11,780 | 16.089초 | 54,784 | 20,711 | 352 | 75,847 | 3 |
| B 파일 참조 | 1,465 | 21.550초 | 53,376 | 21,452 | 524 | 75,352 | 4 |

첫 prompt는 작아졌지만 전체 토큰 차이는 495개(약 0.65%)에 그쳤고 B가 약 34% 느렸으며 비캐시 입력도 741개 많았다. 이는 이 한 쌍의 관찰값이며 반복·무작위화나 동일 캐시/호스트 부하를 보장하지 않는다. 파일을 읽는 추가 왕복 때문에 항상 이득이라는 가설은 지지되지 않았다. 모든 구현에서 근거 축소가 안전하다는 결론도 낼 수 없다.

결정: 하네스 기본은 기존 inline 전달을 유지한다. --evidence-mode reference는 실험 옵션으로 남기고 입력/시도별 계측은 유지한다. 다음 개선은 같은 파일 전체를 옮기는 것보다 작업에 필요한 근거를 정확히 선택하고 재독을 줄이는 방향이다. 대용량/반복 실패 근거의 효과는 아직 미검증이다.

[Langfuse 관측](https://cloud.langfuse.com/project/cmw0ddhw800c0ad0eboi81el1/traces/5c0e9b0880efbfa3f8e0f03a6196431d)은 개별 모델 응답이 아닌 두 CLI agent 실행의 집계 관측이다. 토큰은 원본과 대조했다. 정확한 내부 모델 응답 수는 CLI 스트림에 없어 추정하지 않았다. 준비·검증·조정 대화 비용은 표에서 제외하며 기존 시간·토큰 기록에 별도로 남긴다. 로컬 원시 로그는 .local/evidence-delivery-ab이며 공개 파일에는 원시 대화·비밀 키를 싣지 않는다.
