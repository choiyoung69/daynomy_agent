## 후속 관찰 — 왜 이번에도 시간·토큰이 컸나?

2026-11-04. 기존 원본 세션의 response_id별 token_usage_record와 명령 실행 시각으로 확인했다. 기능·검사 재실행이나 새 계측 도구는 만들지 않았다. 상세 검증·Cloud 링크는 [뉴스 검색 PR의 계측 기록](https://github.com/choiyoung69/daynomy_agent/pull/12)에 있다. 이번 분석 답변의 비용은 아래 완료 작업 집계에서 제외한다.

| 작업 | 요청→최종 응답 | 모델 응답 | 총 토큰 |
| --- | ---: | ---: | ---: |
| 뉴스 검색 개발·검증·게시·마무리 | 약 13분 22초 | 58 | 5,575,192 |
| Langfuse 조사·보충·기록 | 9분 10초 | 31 | 4,962,084 |
| 사용량 질문에 대한 확인·답변 | 28초 | 2 | 373,249 |
| PR 템플릿 수정·본문 정리 | 1분 10초 | 6 | 1,158,368 |

작업 사이 대기를 제외한 네 요청의 경과 합은 약 24분 10초, 97회·12,068,893토큰이다. 실제 명령·모델 추론 시간의 합이라는 뜻은 아니다. 개발의 요청→PR 게시 경계는 12분 45초이며 게시 후 마무리와 구분한다. 개발 전체 캐시/비캐시/출력은 5,429,632 / 122,942 / 22,618, 복구는 4,892,416 / 50,019 / 19,649토큰이다.

### 1. 가장 큰 토큰 요인: 긴 대화 × 응답 횟수

| 부모 대화의 작업 | 호출당 평균 입력 | 입력 중 캐시 비중 |
| --- | ---: | ---: |
| 뉴스 검색 개발·재개 | 94,555토큰 | 97.69% |
| Langfuse 복구 | 159,433토큰 | 98.99% |
| PR 템플릿 수정 | 192,646토큰 | 99.44% |

실험 3의 핵심인 **짧은 인계로 새 대화에서 시작**을 실제로 하지 않았다. HANDOFF를 같은 대화에서 읽은 것은 문맥을 줄인 실험이 아니다. 이후 디버깅·통계 답변·템플릿 수정까지 동일한 누적 대화에서 처리했다. 간단한 템플릿 수정도 6회에 약 116만 토큰을 기록했다. 캐시 재사용은 높았으나 총 입력 수는 줄지 않았다. 이 합계를 청구 금액이나 같은 크기의 비캐시 모델 작업으로 해석하지 않는다. 기본 지침·도구 정보도 입력에 포함되므로 과거 대화만의 정확한 기여율은 계산하지 않았다.

### 2. 시간은 검사보다 조사·조정·중단 경계가 컸다

주요 실제 명령의 프로세스 경과는 RED 14.27초, GREEN+APK/lint 16.31초, 첫 DB/화면 검사 18.91초, 해당 검사 재실행 10.88초다. 합은 약 60초이지만 전체 준비/컴파일/통신을 모두 포괄하는 값은 아니다. 완료 로그를 읽은 명령 0초를 검사 재실행으로 중복 계산하지 않았다.

첫 개발 턴의 마지막 모델 사용량 기록 13:10:53.579와 재개 턴 시작 13:15:28.224 사이에 약 4분 35초의 모델 응답 기록 없는 구간이 있다. GREEN 검사는 13:10:56에 끝났다. 따라서 전체 13분 22초를 모델이 계속 작업한 시간으로 표현하면 잘못이다. 이 구간을 정확한 사용자 대기/호스트 대기로 분해할 근거는 없다.

### 3. 피할 수 있었던 재작업과 과도한 왕복

- 준비에서 gh 미설치·GitHub 쓰기 403·sandbox 실행 거절·F09 KB 준비 범위 제외를 차례로 발견해 경로를 전환했다. 필요한 준비와 원본 계약·독립 검사를 전부 낭비로 세지는 않는다.
- 여러 파일을 통째로 묶어 읽고 도구 메타데이터를 넓게 출력해 잘림이 반복됐다. 복구 중에는 큰 JSON 한 줄 전체를 rg로 출력했다. 출력 문자 수를 토큰으로 환산하지 않더라도 재조회와 문맥 확대의 원인이 됐다.
- 완료된 검사 로그를 다시 읽는 짧은 상태 확인이 남았다. 파일 조회를 묶었어도 호출 사이 판단·응답 왕복 자체가 많았다.
- 화면 검사가 스크롤 밖 버튼을 눌러 재실행했고, 출처 해시가 고정된 README를 고쳐 되돌렸다. PR 본문을 누적 추가해 오래된 상태와 최신 결과를 섞었고 별도 정리 작업이 생겼다.
- 복구에서는 폐기 API·이벤트 개수 가정·Cloud 추정 토큰을 차례로 보정했고, 다른 버전의 CLI·접근 불가 앱까지 조사했다. 필요했던 계측 정확성 확보와 별개로 개발에 가까운 496만 토큰을 사용했다. 기본 훅 실행 검사는 자동 승인 검토에 거절돼 자동 수집의 최종 확인도 남았다.

### 다음 실험에서 바꿀 것

1. 이 파일과 HANDOFF의 필요한 요약만 가진 **새 대화**에서 기능 하나를 시작한다. 새 대화 여부와 첫 응답 입력량을 확인해 이번 조건과 구분한다.
2. 시작 전에 적용 개선·완료 조건·검사 목록을 짧게 기록한다. 기존 계약·직접 수정 파일·선택 KB부터 읽고 실패나 계약 공백이 있을 때만 범위를 넓힌다.
3. 조회는 파일/구간을 제한하고 큰 JSON은 파싱해 필드만 출력한다. 도구 목록은 필요한 이름만 찾고, 검사 완료 후 결과를 한 번 요약한다.
4. 진행 중 상태 조회를 줄이고 완료 결과를 기다린다. 같은 코드·기준·환경에서 성공한 검사는 반복하지 않으며 수정/실패 영향만 재실행한다.
5. PR은 템플릿으로 최종 상태를 한 번 정리한다. 상세 통계는 이 기록에 두고 PR에는 범위가 명확한 요약과 링크만 둔다.
6. 개발과 계측 복구를 분리한다. 수집 상태는 필요한 한 번의 확인으로 판정하고, 복구가 별도 작업이면 그 시간·토큰을 개발 개선 효과에서 숨기지 않는다.

## 하네스 적용 — Issue #13

시작 조건: 기존 CliAgent는 이미 새 ephemeral 세션을 사용했다. 데스크톱의 기존 긴 채팅을 초기화하는 기능은 아니며 과거 하네스를 자동 실행하지 않는다. 기존 adapter/단위 검사를 재사용해 입력 경계만 보완한다.

- 호출 전 기본 32 KiB UTF-8 prompt 제한. 초과하면 모델을 호출하지 않고 파일 참조로 정리하도록 실패한다. 계약을 자동 절단하지 않는다. 이는 토큰 제한이 아니며 실제 필요하면 CliAgent의 max_prompt_bytes를 명시해 조정한다.
- input.json에 크기·문자 수·SHA256·새 세션 정책을 저장한다. 프롬프트 본문을 중복 저장하지 않는다.
- 이전 gate 전체 JSON은 해시로 명명한 prompt-evidence에 보존한다. 다음 입력에는 경로·해시·상태·리뷰 지적을 넣으며 근거를 읽는 의무와 완료 검사는 유지한다.
- attempts.json에 실패한 시도까지 session ID·원본 usage_records를 보존한다. 누락은 빈 목록이며 0 토큰이나 새 실제 모델 호출 수로 환산하지 않는다. 기존 최종 usage 필드는 호환 목적으로 유지한다.
- 검증은 synthetic 단위 검사이며 실제 모델·서버·DB·앱을 실행하지 않는다. 실제 전체 입력/도구 결과/시간 개선은 다음 새 채팅 개발에서 Langfuse와 원본 로그로 관찰한다. 작은 prompt byte 수를 시스템·도구·파일 읽기까지 포함한 전체 입력 감소로 표현하지 않는다.

다음 작업은 HANDOFF의 짧은 요약을 가진 새 채팅에서 시작한다. 구현·검사·복구를 한 채팅에 계속 누적하지 않는다. 채팅 생성/전환은 자동화하지 않았으며 현재 채팅의 입력이 이 코드 수정으로 줄었다고 주장하지 않는다.


하네스 변경 검증: 새 경계 4개 RED(3오류·1실패)→GREEN. timeout 사용량 보존 1개 추가 후 core 47개 통과. 공유 workflow 관련 17개·parallel 21개·admin 67개도 통과했다. admin 최초 26개는 worktree의 Git 제외 원본 부재로 실행 오류였고 원본 경로를 연결한 뒤 실패한 26개만 재검사했다. 실제 원본 파일은 수정하지 않았다. 초기 테스트 작성 명령의 작업 경로 오류로 0개 실행이 있었고 이를 테스트 통과로 세지 않았다. workflow glob이 core를 한 차례 중복 포함한 점은 검사 선택의 남은 낭비다. 모두 로컬 synthetic 검사이며 모델·서버·DB·앱 빌드는 실행하지 않았다.

100,000자 gate 로그를 가진 synthetic 사례에서 전체 gate JSON을 반복 삽입하던 prompt가 100,340→695 UTF-8 bytes로 줄어드는지 확인하고 원본 evidence JSON의 완전 보존을 검증했다. 이 수치는 입력 직렬화 byte 수로, 실제 모델이 파일을 읽는 비용·전체 토큰·시간 절감률이 아니다. 이번 변경 작업 자체도 기존 긴 대화에서 진행했으므로 새 채팅의 효과를 검증한 사례가 아니다.
