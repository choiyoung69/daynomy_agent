## 실험 2 — KB·기존 코드·검사 선택 개선을 Android 의견 보내기에 적용

**작업은 Android F11 ‘의견 보내기’ 구현(PR #10)이었다.** 계정 화면에서 피드백을 입력하고 공개 CSRF 전송을 수행하며, 전송 중 중복 입력/전송을 막고 오류 시 초안을 보존하는 기능이다. 응답이 유실되면 결과 불명으로 표시해 재전송을 차단한다. 별도 A/B 없이 이 기능을 개발하며 개선한 작업 방식의 적용 여부와 비용을 관찰했다.

### ‘개선한 기존 흐름’의 구체적인 내용

| 적용한 개선 | F11에서 실제 사용한 방식 | 유지한 검증·한계 |
| --- | --- | --- |
| 작업에 필요한 KB만 선택 | 피드백 계약·인증/CSRF·JSON·취소에 관한 아래 4문서 선택 | 다른 Android 기능에도 4문서면 충분하다는 뜻은 아님 |
| 준비 확인 중복 줄이기 | 기존 KB 준비/출처 확인 경로를 사용하고 시작 직후 같은 context 준비를 별도 반복하지 않는 흐름 적용 | 완료 시 출처·해시·적용 확인은 유지. 파일 재사용을 모델 캐시 적중으로 세지 않음 |
| 기존 통신과 화면 구조 재사용 | SessionHttpTransport의 CSRF 경로와 기존 Material·ViewModel 구조에 피드백 입력·상태를 연결 | 원문 UTF-16/Java 공백 검증·빈 204·중복 방지·결과 불명 처리 확인 |
| 변경 영향에 맞게 검사 선택 | 피드백 계약 14개 + 기존 세션 7개, APK 빌드와 기존 에뮬레이터 화면 검사 1개 실행 | 다른 플랫폼 전체 빌드와 과거 하네스 실험을 자동 부착하지 않음. 실제 Rust/DB 저장은 미검증 |
| 테스트→구현→리뷰 유지 | 독립 계약에서 RED를 확인하고 고정한 뒤 구현·관련 회귀·읽기 리뷰 수행 | 검사량을 줄여 통과시킨 것으로 비교하지 않음 |

선택한 KB는 다음 네 문서다.

- `knowledge/wiki/projects/daynomy/feedback.md`: 공개 피드백의 원본 입력·전송 계약
- `knowledge/wiki/shared/auth-storage.md`: 쿠키·CSRF와 인증/저장 경계
- `knowledge/wiki/packages/android-kotlin/types-and-json.md`: Kotlin 타입·JSON 경계
- `knowledge/wiki/packages/android-kotlin/async-and-cancellation.md`: 비동기·취소·늦은 응답

실제 순서는 **F11 범위 결정 → 관련 계약/4문서 준비 → 독립 계약 RED → 기존 통신/화면에 구현 → JVM 21개·APK·기기 화면 확인 → 리뷰·PR 게시**였다. 개선한 흐름의 정리는 PR #8, 실제 적용 사례는 PR #10이다. 같은 F11을 이전 방식으로 개발한 대조 실행은 없으므로 전체 절감률은 확인하지 못했다.

## 실험 3 — 전체 본문 전달과 근거 파일 전달 비교

2026-11-04, Issue #13 / PR #14. 같은 Android 선택 해제 회귀·3문서·모델·검사를 사용해 A(전체 근거 본문)와 B(같은 근거 파일 참조)를 실제 실행했다. 각 새 CLI 세션 1회·120초 상한·자동 재시도 없음. 두 구현은 동일했고 고정 JVM 105개가 각각 통과했다. B가 근거 파일을 읽은 것도 확인했다.

| 조건 | 모델 실행 경과 | 캐시 입력 | 비캐시 입력 | 출력 | 총 토큰 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A 본문 | 16.089초 | 54,784 | 20,711 | 352 | 75,847 |
| B 파일 | 21.550초 | 53,376 | 21,452 | 524 | 75,352 |

prompt 11,780→1,465 bytes와 달리 전체 토큰은 495개(0.65%)만 적고 B는 34% 느렸다. 비캐시 입력·출력도 증가했고 shell 명령이 3→4회였다. 같은 과제의 한 쌍이지만 고정 순서 A→B·캐시/부하 차이가 있어 일반적인 절감률로 승격하지 않는다. 정확한 내부 모델 응답 수는 미계측이며 실행 횟수 1회와 구분한다.

**기본값 채택 보류:** 전체 근거 inline을 기본으로 복원하고 --evidence-mode reference를 선택 실험 옵션으로 둔다. 입력 경계·시도별 원본 사용량 기록은 유지한다. 다음 검증은 대용량 근거와 복수 요구사항에서 누락·재작업·전체 시간까지 비교해야 하며, 단순히 첫 prompt가 작다는 이유로 채택하지 않는다. 변경 후 관련 하네스 core 48개가 통과했다.

준비 중 worktree의 원본 경계 문제와 permission_probe에 상대 경로를 전달한 오류가 있었다. 실제 원본 저장소에서 KB 준비를 통과시키고 절대 경로로 기존 쓰기 격리(내부 write·외부 denied)를 확인한 뒤 모델을 호출했다. 보호를 약화하지 않았고 이 준비 비용을 agent 실행 시간에 포함하지 않는다.

근거: experiments/harness-evidence-ab/README.md · results.json · A.diff/B.diff, 원시 로그 .local/evidence-delivery-ab. Langfuse의 집계 관측도 원본과 대조했다. 현재의 긴 조정 대화 비용은 별도이며 두 agent만 저렴했다고 실험 전체가 저렴하다고 표현하지 않는다.

## 실험 4 — 새 채팅에서 기존 웹의 반응형 시안 만들기

### 목적과 변경 방식

짧은 새 채팅의 인계와 관련 파일 조회로 기존 웹 대표 화면 하나의 데스크톱/모바일 시안을 만든다. 별도 A/B·모델 실험이 아니라 실제 UI/UX 작업의 관찰이다. 최초 범위/완료 조건은 작업 전에 기록했고, 최신 사용자 결정에 따라 새 스타일 제안에서 **reference 원본 웹의 충실한 반응형 재현**으로 좁혔다.

## 실험 5 — 공통 하네스에 작업별 선택 KB를 연결한 실제 구현 비교

### 하네스에 실제 연결한 것

- `CliAgent(knowledge_task="query-reset", knowledge_base=...)`가 기존 ensure의 준비·출처 검증을 거쳐 선택 문서 원문만 실제 prompt에 삽입한다. caller가 수동으로 3문서를 붙이는 비교가 아니다.

- 큰 상태 stdout은 짧은 상태와 state.json 경로로 바꾸며 실제 질문·실패 근거는 삭제하지 않는다. 모델이 긴 로그를 다시 읽고 표를 만드는 왕복을 줄이기 위한 변경이다.
- --summarize-run 모드에서 지정한 조정 턴 원본과 모든 CLI 시도의 사용량을 합산한다. 동일 응답/복사된 agent 관측은 중복 합산하지 않고, 실패/누락·cached 필드 부재는 unknown으로 표시한다. 기록 모드는 Workflow/모델/검사/DB를 실행하지 않는다.
- 새 비용 검사5개 RED에서4오류·1실패를 확인한 뒤 구현했다. 중복·CLI 무실행·누락 필드 회귀와 자동 종료 보고 검사를 추가해 최종 core62개 통과. 기존 실패 gate/독립 리뷰/불변 기준 검사는 그대로 통과했다. 단계 계측 자체는 합성 상태 검사이며 과거 수동 실행의 단계 시간을 소급해 만들지 않았다.

### 이전 실험 5의 전체 비용 재집계

기존 실제 agent 2개와 그 작업의 완료된 조정 턴을 한 CLI 명령으로 재집계했다. 원본 response_id별 값과 독립 합계가 일치했다. 명령 실행 약0.080초, stdout306 bytes, 새 모델 호출0회였다. 이 수치는 **사후 집계 명령만의 실행 시간**이며 전체 개발 시간이0.08초가 됐다는 뜻이 아니다.

| 완료된 요청의 합계 | 6,040,960 | 69,770 | 32,321 | 6,143,051 |

요청 시작→최종 응답은801.343초(약13분21초)다. 이전의752.4초(약12분32초)는 PR 게시까지이며, 부모16응답/5,190,823토큰도 게시 시점 부분 집계였다. 이번 값은 최종 응답까지 부모18응답과 CLI agent2실행을 포함한다. CLI 내부 모델 응답 수는 미계측이라 합쳐서20회 모델 호출이라고 표현하지 않는다. 부모 경과에 agent 시간을 다시 더하지 않았다. 부모 토큰이 모두 낭비라는 뜻은 아니며 구현/검증/기록 작성도 포함한다.

두 agent의265,536토큰은 기존 Langfuse 대조값과 같고, 부모는 로컬 원본 집계다. 부모 전체를 새로 Cloud에 보충하지 않았다. 재현 수치는 experiments/workflow-cost-replay/results.json, 실제 보고서는 .local/task-kb-ab/cost-summary.json/md에 있다. 과거 수동 준비/게시의 단계별 시간은 미계측이다.

### 효과와 한계

자동 보고로 긴 원시 로그를 여러 번 읽어 집계·정정하는 절차를 한 번의 비모델 명령으로 대체할 수 있게 됐다. 기존 Workflow 실행은 단계 상태와 종료 요약을 자동으로 남긴다. 그러나 현재 데스크톱 대화의 누적 문맥이나 모든 개발 준비가 자동으로 줄어드는 기능은 아니다. 실제 다음 개발의 전체 시간/토큰 절감은 아직 미검증이다. 새 채팅의 짧은 인계와 기존 실행 경로를 사용하고, 보고서 한 번 확인→기존 문서/PR에 링크하는 흐름으로 적용해야 한다. 새 모델 비교를 만들어 검증 비용을 늘리지 않았다. 이번 개선 작업 자체 비용도 아래에 별도로 기록한다.


실험6 PR: https://github.com/choiyoung69/daynomy_agent/pull/20. 이번 개선 자체 요청→PR 게시 1057.8초. 자동 집계한 부모 부분 사용량: 응답 12회, 캐시 입력 4,397,824·비캐시 입력 4,728·출력 36,534·총 4,439,086토큰. 별도 구현 agent 재호출은 하지 않았다. 현재 턴이 끝나지 않아 complete=false이며 미기록 게시 응답·이후 기록/최종 답변은 제외한다. 종료 후 같은 보고 명령으로 갱신할 수 있다. 이번 개선 자체 비용도 절감에서 숨기지 않는다.


실험6 이번 개선의 종료 후 최종 집계: 요청→최종 응답 1192.071초, 부모 응답 15회, 캐시 입력 5,552,896·비캐시 입력 5,509·출력 41,330·총 5,599,735토큰. 이 요청에서 별도 구현 agent는 호출하지 않았다. 앞선 PR 게시 시점 부분 집계와 경계를 구분한다. 게시 대기 중 짧은 상태 조회를 반복한 낭비도 이 값에 포함된다. 이 값은 로컬 원본이며 Cloud 전체 대조값은 아니다. 기존 summarize_run으로 턴 종료 후 자동 집계했고 모델·네트워크·Git 게시를 추가하지 않았다. 근거 .local/overhead-change/cost-summary.json/md.
